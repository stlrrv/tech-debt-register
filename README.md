# Реестр приоритезации задач

Веб-приложение для планирования задач, которое закрывает ограничение Bitrix24: в Bitrix удобно исполнять задачи, но неудобно гибко приоритизировать их между собой.

Реестр решает эту проблему:
- считает ценность по единой формуле;
- визуализирует задачи на матрице ценность/усилия;
- показывает отдельную очередь бэклога;
- даёт прозрачный публичный срез для сотрудников;
- в следующем этапе будет читать задачи из Bitrix24 и использовать Bitrix как источник задач.

## Что уже есть

- Бизнес- и технические задачи в одном интерфейсе
- Расчёт ценности по формуле:
  `Ценность = (Процесс × 3) + (Откладывание × 2) + Охват + Дедлайн`
- Расчёт поля `Процесс` по фактической стоимости процесса:
  - `Затраты времени/мес = операций_в_день × время_на_операцию × кол-во_человек × рабочих_дней`
  - `Деньги/мес = Затраты_времени_в_часах × средняя стоимость часа сотрудника`
- Квадранты для задач спринта
- Отдельная очередь для задач вне спринта
- JSON import/export
- Read-only сценарий для публичного просмотра

## Текущая логика продукта

Источник правды по приоритизации: реестр.

Источник задач на этапе интеграции: Bitrix24.

Ожидаемый сценарий работы после интеграции:
1. Все активные задачи из Bitrix24 подтягиваются в реестр.
2. Реестр делит их по двум скрамам:
   - `1С`
   - `Web`
3. Внутри каждого скрама есть:
   - отдельный спринт
   - отдельная очередь
4. Задачи в спринте попадают в квадранты.
5. Задачи вне спринта отображаются в очереди с пользовательским номером позиции.

## Разделение по скрамам

Принято решение поддерживать два независимых скрама:
- `1С` — Bitrix ID `189`
- `Web` — Bitrix ID `135`

Рекомендуемая модель интерфейса:
- верхние вкладки `Web` / `1С`
- внутри каждой вкладки свои фильтры, свой спринт, своя очередь и своя сводка

Это нужно для того, чтобы задачи двух команд не смешивались ни в матрице, ни в очереди.

## Очередь

Очередь нужна не для исполнения, а для прозрачности и приоритизации.

В очереди:
- отображаются все активные задачи проекта, которые не находятся в текущем спринте;
- у каждой задачи есть:
  - ID задачи Bitrix24
  - пользовательский номер позиции в очереди
  - рассчитанная ценность
  - поля реестра для приоритизации

Важно:
- `bitrixTaskId` и `queuePosition` — разные вещи;
- `bitrixTaskId` приходит из Bitrix и не меняется;
- `queuePosition` задаётся в реестре и нужен внешним пользователям, чтобы понимать место задачи в очереди.

## Интеграция с Bitrix24

На текущем этапе принято решение:
- читать задачи из Bitrix24;
- не писать изменения обратно в Bitrix24;
- хранить приоритизацию, очередь и визуализацию в реестре.

## Структура данных реестра

### Общие поля задачи

- `bitrixTaskId`: ID задачи в Bitrix24
- `projectKey`: `web` или `onec`
- `type`: `business` или `tech`
- `taskNumber`: номер задачи для отображения, если используется отдельно
- `title`
- `description`
- `customerDepartment`
- `direction`: `web`, `onec`, `common`
- `registryStatus`: `new`, `candidate`, `planned`, `in_progress`, `done`, `deferred`
- `queuePosition`
- `size`: `S`, `M`, `L`, `XL`
- `delayScore`
- `impactScore`
- `deadlineScore`
- `operationsPerDay`
- `minutesPerOperation`
- `peopleCount`
- `workDaysPerMonth`
- `hourlyRate`
- `processScore`
- `processMonthlyHours`
- `processMonthlyMoney`
- `createdAt`
- `updatedAt`

### Поля бизнес-задачи

- `businessGoal`
- `expectedOutcome`
- `externalDependencyNote`

### Поля технической задачи

- `consequence`
- `riskLevel`
- `burnHorizon`
- `techCategory`
- `needsDecomposition`
- `needsTechLead`
