# ТЗ: интеграция реестра с Bitrix24

## 1. Контекст

Bitrix24 используется как рабочая система исполнения задач, но не закрывает потребность команды в гибкой приоритизации между задачами.

Реестр нужен для трёх целей:
- считать ценность задач по внутренней формуле;
- визуализировать задачи на матрице ценность/усилия;
- давать прозрачный публичный срез для внутренних пользователей.

После интеграции Bitrix24 становится источником задач, а реестр остаётся источником приоритизации и визуализации.

## 2. Цель этапа

Подготовить реестр к интеграции с Bitrix24 и описать архитектуру первого рабочего релиза, в котором:
- задачи читаются из Bitrix24;
- задачи автоматически раскладываются по двум скрамам;
- спринт и очередь отображаются раздельно;
- реестр не пишет изменения обратно в Bitrix24;
- внешние пользователи могут видеть прозрачную очередь и текущий спринт.

## 3. Границы этапа

### Входит в этап

- разделение реестра на два скрама;
- импорт активных задач из Bitrix24;
- отображение всех активных задач в очереди или спринте;
- отдельная логика очереди и отдельная логика спринта;
- подготовка модели данных под интеграцию;
- документация;
- архитектурная схема;
- требования к UI и поведению.

### Не входит в этап

- запись изменений из реестра обратно в Bitrix24;
- автоматическое изменение статусов задач в Bitrix24;
- двусторонняя синхронизация;
- webhook-обработчики и события в production;
- авторизация пользователей внутри реестра;
- распределение задач по исполнителям.

## 4. Бизнес-правила

### 4.1. Скрамы

В системе есть два независимых скрама:
- `1С` — Bitrix ID `189`
- `Web` — Bitrix ID `135`

Реестр должен отображать их раздельно, чтобы задачи не смешивались.

### 4.2. Визуальная модель

Для каждого скрама должны существовать:
- отдельная вкладка;
- отдельный спринт;
- отдельная очередь;
- отдельная сводка;
- отдельные фильтры внутри вкладки.

### 4.3. Источник задач

Источник задач — Bitrix24.

В очередь или спринт должны попадать все активные задачи выбранного проекта/скрама.

Под "активными" в рамках ТЗ понимаются задачи, которые:
- относятся к нужному проекту;
- не завершены;
- не удалены;
- доступны через API задач.

### 4.4. Разделение на очередь и спринт

Принятое правило:
- задачи, находящиеся в спринтовых стадиях Bitrix24, отображаются в блоке `Спринт`;
- остальные активные задачи отображаются в блоке `Очередь`.

Так как конкретная стадийная схема может отличаться между проектами, реализация должна использовать настраиваемое правило маппинга стадий:
- `queueStages[]`
- `sprintStages[]`

Пример, который уже известен из бизнеса:
- `Задачи без статуса`
- `Прием и анализ`

Эти стадии относятся к состояниям до спринта и, вероятно, должны попадать в очередь. Конкретный маппинг фиксируется разработчиками после сверки с реальными полями API на портале.

## 5. UX-требования

## 5.1. Вкладки скрамов

На верхнем уровне интерфейса должны быть вкладки:
- `Web`
- `1С`

При переключении вкладки меняются:
- список задач;
- очередь;
- квадранты;
- сводка;
- сортировки и фильтры.

По умолчанию открывается последняя выбранная вкладка или `Web`.

## 5.2. Очередь

Очередь должна отображать все активные задачи скрама, которые не попали в спринт.

Для каждой задачи в очереди должны быть видны:
- ID задачи Bitrix24;
- название;
- статус Bitrix24 / статус реестра;
- пользовательский номер в очереди;
- рассчитанная ценность;
- базовые атрибуты фильтрации.

### Правила по номеру в очереди

Текущее решение:
- номер очереди не редактируется прямо в строке списка;
- номер очереди редактируется только в карточке/форме редактирования задачи;
- после сохранения задачи очередь пересортировывается.

Причина:
- так меньше случайных изменений;
- логика изменения позиции сосредоточена в одном месте;
- карточка задачи остаётся единой точкой редактирования.

### Сортировки очереди

Очередь должна поддерживать как минимум:
- сортировку по `queuePosition`;
- сортировку по `bitrixTaskId`;
- сортировку по ценности.

Рекомендуемое поведение по умолчанию:
- если заполнен `queuePosition`, сортировать по нему;
- если `queuePosition` не заполнен, показывать задачу ниже задач с заполненной позицией;
- вторичный порядок — по ценности;
- альтернативный режим сортировки — по номеру задачи Bitrix24.

## 5.3. Спринт

В блок `Спринт` попадают задачи, которые в Bitrix24 уже находятся в спринте.

Кнопка `Добавить в спринт` на этом этапе не нужна, потому что бизнес-решение уже принято:
- задача должна считаться спринтовой не по действию в реестре,
- а по фактическому состоянию в Bitrix24.

Следствие:
- реестр не переводит задачу в спринт самостоятельно;
- реестр только отражает текущее состояние Bitrix24 и даёт дополнительно заполнить поля приоритизации.

## 5.4. Редактирование задачи

При открытии задачи из очереди или спринта должна открываться форма редактирования полей реестра.

Через неё редактируются:
- оценки приоритизации;
- факты для расчёта процесса;
- тип задачи;
- отдел-заказчик;
- ожидаемый результат / технический контекст;
- номер позиции в очереди.

Не редактируются вручную:
- `bitrixTaskId`;
- принадлежность к скраму, если она пришла из Bitrix;
- системные поля Bitrix, если они синхронизируются только на чтение.

## 7. Требования к синхронизации с Bitrix24

## 7.1. Общий принцип

Синхронизация односторонняя:
- Bitrix24 -> Реестр

Реестр не должен менять данные в Bitrix24 на этом этапе.

## 7.2. Что читаем из Bitrix24

Нужно подтягивать:
- ID задачи;
- название;
- описание;
- статус;
- стадию;
- группу / проект;
- даты изменения;
- при наличии:
  - ответственного;
  - дедлайн;
  - теги;
  - пользовательские поля, если в них хранится полезная классификация.

## 7.3. Привязка задачи к скраму

Базовое правило первого этапа:
- если `GROUP_ID = 135`, задача относится к `Web`;
- если `GROUP_ID = 189`, задача относится к `1С`.

Если на реальном портале скрам выражен не только через `GROUP_ID`, разработчики должны заложить адаптер маппинга, но внешний контракт реестра не менять.

## 7.4. Определение, где показывать задачу

Псевдологика:

```text
если задача завершена -> не показывать
если задача относится к sprintStages -> показывать в спринте
иначе -> показывать в очереди
```

## 7.5. Слияние данных

При обновлении задач из Bitrix24:
- системные поля Bitrix обновляются из API;
- локальные поля приоритизации сохраняются;
- запись матчится по `bitrixTaskId`.

Если задача пришла из Bitrix впервые:
- создаётся новая запись реестра;
- локальные поля получают значения по умолчанию.

Если задача исчезла из выдачи активных задач:
- не удалять её физически немедленно;
- пометить как неактивную или скрыть из текущего списка;
- сохранить локальную историю.

## 7.6. Массовая загрузка

Нужно учитывать лимиты API Bitrix24.

Требования:
- использовать постраничную загрузку списков;
- предусмотреть `batch` там, где он уместен;
- не дублировать запросы без необходимости;
- логировать ошибки синхронизации.

## 8. Архитектура

## 8.1. Рекомендуемый вариант

Рекомендуемая архитектура для этапа интеграции:

1. `Frontend`
   - текущий Vue/Vite интерфейс реестра
   - вкладки `Web` / `1С`
   - матрица, очередь, фильтры, сводка

2. `Sync adapter`
   - модуль синхронизации Bitrix24
   - получает активные задачи
   - нормализует данные
   - маппит стадии в `queue/sprint`
   - сливает их с локальными полями реестра

3. `Local registry store`
   - JSON или другое локальное хранилище текущего приложения
   - хранит локальные поля приоритизации
   - хранит пользовательские номера очереди

4. `Bitrix24 API client`
   - отвечает за авторизацию, вызовы REST, пагинацию, лимиты и batch

## 8.2. Почему не только статическая HTML-страница

По официальной документации Bitrix24:
- статичное локальное приложение на HTML/JS может обращаться к REST API;
- но статичное приложение не может получать события;
- серверное приложение позволяет и REST-вызовы, и серверную логику.

Поэтому:
- для быстрого прототипа допустим статичный клиент с ручной синхронизацией;
- для нормальной интеграции лучше закладывать серверный слой или отдельный sync-модуль.

## 8.3. Минимальная техническая схема

Вариант для первого рабочего релиза:

```text
Bitrix24 API
  -> sync service / adapter
  -> normalized registry model
  -> UI registry tabs (Web / 1C)
```

## 9. Технические задачи для разработки

## 9.1. UI

- добавить вкладки `Web` / `1С`
- ограничить видимость задач активной вкладкой
- разделить очередь и спринт внутри каждой вкладки
- убрать inline-редактирование позиции из блока очереди
- перенести `queuePosition` в форму редактирования задачи
- добавить сортировку очереди по:
  - позиции
  - ID Bitrix
  - ценности

## 9.2. Data layer

- расширить модель задачи bitrix-полями
- добавить `projectKey`
- добавить маппинг `GROUP_ID -> projectKey`
- добавить маппинг `bitrix stage -> sprint/queue`
- реализовать merge по `bitrixTaskId`

## 9.3. Integration layer

- создать клиент Bitrix24 API
- реализовать загрузку задач по проекту / группе
- предусмотреть пагинацию
- предусмотреть batch
- предусмотреть конфиг с ID проектов:
  - `web = 135`
  - `onec = 189`

## 9.4. Public transparency

- сохранить read-only сценарий
- показывать внешним пользователям:
  - текущий спринт
  - очередь
  - номер позиции задачи
  - сводку
- не показывать внутренние детали интеграции и служебные поля

## 10. Нефункциональные требования

- приложение должно работать как на GitHub Pages, так и в Bitrix24 как приложение;
- структура кода должна позволять добавить реальную интеграцию без полной переписи UI;
- конфигурация проектов и стадий не должна быть захардкожена только в шаблоне, нужен отдельный слой конфигурации;
- поведение должно быть одинаковым в read-only и edit mode, кроме собственно редактирования;
- при ошибке синхронизации пользователь должен видеть предыдущее валидное состояние, а не пустой экран.

## 11. Открытые технические вопросы для реализации

Эти вопросы не блокируют ТЗ, но должны быть проверены разработчиками на живом портале:
- каким именно REST-методом удобнее получать активные задачи по нужному скраму;
- в каких полях API доступны текущие стадии задач для скрама;
- как точнее определять принадлежность задачи к активному спринту;
- какие scope нужны порталу для чтения задач и, возможно, групп/проектов;
- нужен ли отдельный серверный слой сразу или допустим промежуточный клиентский прототип.

## 12. Рекомендация по реализации

Рекомендую делать не просто "фильтр по Web и 1С", а именно две изолированные вкладки с независимыми очередями и квадрантами.

Рекомендую также сделать позицию в очереди полем карточки задачи, а не inline-инпутом в списке.

Если позже захочется ещё удобнее управлять очередью, следующим шагом можно добавить:
- кнопки `поднять / опустить`;
- drag-and-drop;
- автоматическую перенумерацию внутри текущего скрама.
